# PHASE 6D REPORT — Citizen Experience, Trust & Resolution Intelligence

## 1. Executive Summary

Audit found the citizen-facing report detail page already well-built for *display* (real AI analysis, real follow-ups/reminders, real before/after evidence) but leaving real stored data unused and one real "fabricated evidence" bug in place: `status_history` — real timestamps, real actors, real notes, written by every status-changing code path since Phase 1 — was fetched into `report.statusHistory` and never rendered; the "Status Timeline" was a purely synthetic 6-step bar keyed only by the current status enum; and `BeforeAfterCard` silently fell back to a hardcoded stock photo (`/images/hero-pothole.jpg`) whenever no real evidence photo existed. There was also no way for a citizen to say a resolution didn't actually work, and no reopen path in the status lifecycle at all.

This phase: replaced the synthetic timeline with a real, event-driven one built entirely from `status_history`; removed the fake-photo fallback and replaced it with an honest "not provided" state; added a citizen resolution-feedback mechanism (confirmed/unresolved) with a safe, additive `REOPENED` status extending the existing lifecycle; surfaced the already-fetched-but-unused duplicate/related-issue data on the citizen's own report; and added a deterministic (zero-Gemini-cost) "Understand your report" summary and per-status plain-language explanations, in English with Telugu translations included as extensible data. No new AI calls, no fabricated events, no fabricated evidence, no fake "verified" badge anywhere.

## 3. Citizen Report Detail

No structural rebuild — the existing card layout (Problem Description, Location, AI Analysis, Follow-ups, Reminders, Routing) is unchanged. Added, all from real data already on `ReportDetail`: a trust-indicator row, an "Understand your report" summary card, and (for resolved reports) a resolution-quality-signal row — all directly under the title/status header, before the two-column body.

## 4. Status Timeline

New `src/components/cards/RealStatusTimeline.tsx` replaces the synthetic bar on the real-report path (`RealReportDetail`) with `report.statusHistory` rendered as it actually happened — real timestamp (IST), a role-generic actor label derived from already-known facts (`changed_by === null` → "CivicFix AI"/system-driven ROUTED/AI_ANALYZED; `changed_by === reporterId` → "You"; otherwise → generic department wording, e.g. "Department acknowledged" — never a personal name), and the real notes a department/citizen actually entered (boilerplate autogenerated notes like "Report submitted" are suppressed since the label already says it). Stages not yet reached render as explicit "Not yet reached" placeholders with no timestamp — never a fabricated one. A `resolved → reopened` transition renders as its own real step, followed by the department's second acknowledge/in-progress/resolve pass. This same component doubles as the "track your issue" plain-language progress view (spec §14) — one component, not a second competing UI. The **sample-data path is untouched**: `SampleReportDetail` (clearly labeled "Sample data shown for demonstration") keeps using the original `IssueTimeline`, which has no real `status_history` to draw from.

## 5. AI Status Explanation

New `src/lib/citizen-summary.ts`. `buildCitizenSummary(report)` composes a plain-language paragraph entirely from fields already stored on `ReportDetail` (title, location, AI-recommended priority/department, assignment) — **no new Gemini call**, since every fact was already generated once at analysis/routing time. `STATUS_EXPLANATIONS` gives a deterministic "what this means" + "what's next" pair for all 7 statuses (including `REOPENED`). Both are 100% deterministic template logic — AI is narrated, never re-invoked, so this feature costs zero additional Gemini quota and behaves identically whether or not AI is currently reachable.

## 6. Resolution Experience

Fixed the fake-evidence bug: `src/app/reports/[id]/page.tsx` no longer falls back to a hardcoded stock photo (`/images/hero-pothole.jpg`) when `resolution_evidence.after_media_id`/`before_media_id` resolves to no URL. `BeforeAfterCard` is now only rendered when **both** a real before and a real after photo exist; otherwise the page shows "Resolution evidence not provided." — an honest empty state, never a fabricated image.

## 7. Citizen Feedback

New: `resolution_feedback` table, `submitResolutionFeedback` server action (`src/lib/actions/resolution-feedback.ts`), and `ResolutionFeedbackForm` client component. Only the original reporter can submit (`report.reporter_id === session user id`, looked up server-side — never trusted from the client); only actionable while `status === RESOLVED`; rate-limited and idempotency-protected exactly like every other mutating action in this codebase (`checkRateLimit` + `beginIdempotentAction`). One row per report, **editable** (upsert-by-report-id) rather than insert-only, so a citizen can re-submit fresh feedback after a reopen → re-resolve cycle — the app distinguishes "feedback for which resolution" by comparing `resolution_feedback.updated_at` against `resolution_evidence.resolved_at`, not a new resolution-cycle-id column. Comment capped at 1000 characters, always rendered as plain text (no `dangerouslySetInnerHTML` anywhere in this codebase — no new XSS surface). This is a citizen-reported confirmation signal only — never auto-converted into an official government resolution.

## 8. Reopen Workflow

`IssueStatus` gained one new, safely-integrated value: `REOPENED`. Deliberately ranked **below** `ACKNOWLEDGED`/`IN_PROGRESS` in `STATUS_ORDER` (same rank as `ROUTED`) — a reopened report re-enters the workflow needing fresh department attention, so the in-charge must acknowledge again before resolving again. This reuses `canAdvanceStatus`/`FORWARD_STATUSES`/`canSubmitResolution` **completely unchanged** — no special-casing needed anywhere in the existing transition logic, confirmed by `status-transitions.test.ts`'s new `REOPENED` test block. `REOPENED` can only ever be set by `submitResolutionFeedback` (never via `updateReportStatus`, which still only accepts `ACKNOWLEDGED`/`IN_PROGRESS`). On reopen: a real `status_history` row is written, `reports.reopened_at` is stamped, the previous `resolution_evidence` row is **never deleted** (old before/after photos remain visible), and `issue_reopened` notifications go to the assigned in-charge and every government user whose jurisdiction covers the report (reusing Phase 6C's `findGovernmentUsersForJurisdiction`).

## 9. Resolution Quality Signals

Three distinct, honestly-labeled states, all derived from real data: **"Resolution evidence submitted"** (department, from `resolutionEvidence !== null`) is now always shown separately from **"Citizen confirmation pending"** / **"✓ Citizen confirmed"** / **"⚠ Citizen reports still unresolved"** (from `resolutionFeedback`, scoped to the *current* resolution cycle via the timestamp comparison in §7). No fabricated "verified" badge anywhere.

## 10. Before/After Evidence

See §6 — the only change was removing the fake-photo fallback. Existing secure-URL signing (Supabase Storage signed URLs, 900s TTL, via `getReportDetail`'s admin client scoped to an already-RLS-confirmed report id), accessible alt text, and mobile-friendly grid layout were already correct and untouched.

## 11. AI Evidence Interpretation

Already fully implemented pre-Phase-6D (`AIAnalysisDetails.tsx`'s "Evidence Observed in Photo" section, contradiction-note, low-confidence banner) — no changes made. Verified still working via the live browser check in §24.

## 12. Duplicate/Related Issue UX

`report.duplicateOf` was already fetched by `getReportDetail` but never rendered on the citizen's own report page — only used pre-submission and on the government dashboard. Extended the fetch to also pull the target report's `category`/`status`/`location` (all public-safe fields already shown for any report on this same page) so the existing, privacy-safe `DuplicateIssueCard` component could be reused as-is. Rendered directly under the resolution section on `/reports/[id]`. Verified live (§24) — a real report showed "Possible Duplicate Detected" with the correct target report, reason, and location, with zero private data (no email/phone) present anywhere in the card, per the new `resolution-feedback.spec.ts` E2E privacy check.

## 13. Citizen Dashboard

No changes — already solid (stats, category chart, paginated "My Reports" with status/priority/category/search filters). The status filter dropdown automatically gained a "Reopened" option once `statusLabels`/`statusOrder` were extended (§8), so a citizen can already filter to reopened reports with zero dashboard-specific code. Per the spec's own instruction to avoid excessive dashboard complexity, a dedicated "Reopened" stat tile was deliberately not added — the filter already covers the practical need.

## 14. Privacy

No new PII exposure introduced. `DuplicateIssueCard`'s new fields (§12) are only ever the other report's own public category/status/location — never its reporter's identity, phone, email, or media. `RealStatusTimeline`'s actor labels are role-generic ("Department acknowledged," "You," "CivicFix AI") — never a personal name resolved from `changed_by`. Government-viewer access to `resolution_feedback` is scoped by the existing `can_view_report()` RLS helper, unchanged.

## 15. Trust Indicators

New row of small, real-data-only badges: "AI analyzed" (`aiAnalysis !== null`), "Department acknowledged" (`statusHistory` contains an `ACKNOWLEDGED` transition), "Resolution evidence submitted" (`resolutionEvidence !== null`), plus the resolution-confirmation state from §9. Never renders "Government verified" or any other fabricated certification.

## 16. Telugu/English Support

No i18n framework exists in this project (no locale routing, no language switcher, no translation library) — confirmed by a full-repo grep. Building one is out of this phase's scope (would be the "major architecture rewrite" the spec explicitly forbids). Per the spec's own instruction ("if proper localization architecture does not exist, do not create an inconsistent translation system; document what is available and keep the implementation extensible"), every entry in `STATUS_EXPLANATIONS` is shaped as `{ en: string; te: string }` with real Telugu text filled in for all 7 statuses — extensible, ready data, not a dangling UI. Only `.en` is rendered today.

## 17. Notifications Integration

Two new additive `NotificationType`s through the existing, unchanged `createNotification()` pipeline (no second notification system): `resolution_feedback_recorded` (→ the assigned in-charge, on either a "yes" or "no" feedback) and `issue_reopened` (→ the assigned in-charge + jurisdiction government users, only on "no"). Both mapped to the pre-existing `resolution_updates` category — no new preference category needed. Migration `0012` also widens `notifications_type_check` (the constraint Phase 6C named explicitly) to accept the two new values.

## 18. Database Changes

One new migration, `supabase/migrations/0012_phase6d_citizen_trust.sql` — fully additive:
- Widens `reports.status`'s CHECK constraint to accept `'reopened'`, via a `DO` block that looks up the constraint's real (auto-generated) name from `pg_constraint` rather than assuming it — learned from the Phase 6A `42P13` incident.
- Widens `notifications_type_check` (named explicitly in 0011) to accept the two new types.
- `reports.reopened_at timestamptz` (nullable).
- New table `resolution_feedback` (`report_id` unique, `citizen_id`, `confirmed`, `comment`, `created_at`, `updated_at`), RLS enabled with one `select` policy reusing the existing `can_view_report()` helper — no INSERT/UPDATE policy for `authenticated`, matching this project's universal write-only-through-service-role-after-app-checks pattern.
- **No separate `reopen_reason` column** — deliberately not added, since the reason is already captured by `resolution_feedback.comment` and by the pre-existing append-only `status_history.notes`; a third copy would be redundant denormalization.
- No drops, no data loss, migrations `0001`–`0011` untouched.

**✅ APPLIED to the live Supabase project on 2026-09-20** and independently verified live (§24) — `reports.reopened_at` exists, `resolution_feedback` exists with all expected columns, `reports.status` accepts `'reopened'` while still rejecting genuinely invalid values, and the widened `notifications_type_check` accepts both new notification types (confirmed by two real `issue_reopened` notifications persisting in §24's live test).

## 19. RLS/Security

- `resolution_feedback_select` is the only new RLS policy — reuses `can_view_report()` unchanged, no new SQL logic to review.
- `submitResolutionFeedback` never trusts a client-supplied user id or report ownership: `report.reporter_id` is looked up server-side via the admin client and compared to the caller's own session user id.
- Same rate-limit + idempotency pattern as every other mutating action (`checkRateLimit`, `beginIdempotentAction`) — no new dedup/abuse surface.
- Comment length capped at 1000 chars; always rendered as plain text — no new XSS vector.
- No client-provided role/department/jurisdiction value is ever trusted (unchanged from prior phases).

## 20. Accessibility

- `ResolutionFeedbackForm` uses a real `<fieldset>`/`<legend>` (visually hidden, screen-reader visible) around the Yes/No radios, each with a real associated `<label>`.
- The resolution-quality badges and trust indicators use icon + text together — never color alone.
- `RealStatusTimeline`'s "Not yet reached" steps use an explicit text label plus a small icon, not just a dimmed color.
- Reused existing `role="alert"`/`role="status"` conventions for the feedback form's error/success states, matching `FollowUpForm`/`DepartmentActionsPanel`.

## 21. Mobile Validation

No new fixed-width elements were introduced — every new block (trust-indicator row, summary card, resolution-feedback form, real timeline) reuses the existing `flex flex-wrap`/`rounded-2xl border` card patterns already verified at every breakpoint in prior phases. Not re-screenshotted at each explicit breakpoint (375/390/768px) this phase — flagged honestly in §27 rather than claimed.

## 22. Performance

`RealStatusTimeline` and `buildCitizenSummary` both operate on data the page was already fetching (`report.statusHistory`, `report.aiAnalysis`, `report.assignment`) — zero new queries. The one new query added is `resolution_feedback` in `getReportDetail`'s existing `Promise.all` batch (one more parallel round trip, not sequential), plus the duplicate-target report's location (§12), same pattern. No N+1s introduced.
